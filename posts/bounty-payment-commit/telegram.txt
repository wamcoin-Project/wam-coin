Somebody in this community read the mining pool's code — without running
any of it — and found that the pool could pay the same miners a second time.
He has been paid for it: the fifth time somebody has done real work for WAM
and taken the coin as the payment for it.

The pool broadcasts a payment, writes a marker saying one is in flight, then
commits the balance decrements to redis. That commit was an ioredis
pipeline(), and exec() on a pipeline *resolves* with [error, result] pairs —
a command that fails arrives as data, not as a thrown error. So a failed
commit threw nothing, paused nothing, and left every balance standing. Ten
minutes later the next run paid the same miners again from the same balances.
The marker written for exactly this case was read in one place in the whole
repository, at startup, so it only ever spoke after a restart.

Three more in the same report. The share accounting had the identical shape,
so a miner could be told valid:true for a share that was never recorded.
recordBlock asked two of the three places a block can already be accounted
for and not the third. And shutdown did not wait for the accounting chain, so
a restart arriving between a block being accepted and its payout being
recorded lost it the way a power cut would — except that a restart is
ordinary.

All four are fixed, and each is held down by a regression test that was run
against the old code to confirm it fails there.

10,250 WAM — 10,000 for the payment commit and 250 for the share, both rungs
he classified himself under the table as it stood that day; the table was
lowered hours later, with the reasons written out on the same page. Ten transactions of 1,025 each, all in block 37,299:
consensus pays the treasury 2.5 WAM per block and never consolidates it, so
one transaction would have been about 4,100 inputs and 591 KB, six times what
any node will relay.

Every amount, the reasoning behind it and every transaction id:
https://wamcoin.org/security/
